MULTITHREADED VIDEO COMPRESSOR | TECHNICAL REPORT
Abstract
This report analyses the public Multithreaded Video Compressor repository as a C11/POSIX-
threads educational codec. The encoder accepts raw planar 8-bit YUV420 data, divides each
plane into 8×8 blocks, predicts blocks from reconstructed top and left boundaries, transforms
residuals using a separable orthonormal DCT-II, quantizes coefficients, applies zig-zag run-
length encoding, and Huffman-codes the per-frame symbol stream. A bounded pthread work
queue schedules block-row jobs; mutex-protected progress and condition-variable broadcasts
enforce the top-neighbour dependency; a separate reorder writer preserves frame-number
order. The resulting `FRM1` stream is project-specific and is not a JPEG or H.264 bitstream.
The retained benchmark CSVs support an original one-to-eight-worker speedup of 3.60×
(0.540 s to 0.150 s) for a three-frame 1280×720 input. The same input size (4,147,200 bytes)
and retained compression-comparison CSV support 105,453 output bytes with prediction
enabled (39.33:1; 97.46% space saving) and 150,083 bytes with prediction disabled (27.63:1;
96.38% space saving). The later synchronization-granularity campaign is treated separately
because its averages come from another run campaign. Source and retained-data arithmetic
were audited, but an executable clone and the production input/output samples were not
available locally for rerunning tests or recomputing PSNR. Repository-reported test and
Helgrind outcomes are therefore clearly distinguished from independently reproduced
evidence.
Keywords: video compression, YUV420, discrete cosine transform, Huffman coding,
pthreads, wavefront scheduling, performance measurement.

1. Introduction
Video data is costly to store and transmit, while compression must balance bit rate,
reconstruction error, encoder complexity, and execution time. This project isolates two
concerns that are often hidden inside production codecs: how a lossy block codec
reconstructs its own prediction state, and how that dependency-constrained work can be
parallelized without changing encoded output or corrupting frame order. The repository is a
teaching implementation that makes those steps visible in C rather than a replacement for a
standardized codec [1].
Its input is raw, planar, 8-bit YUV420. The luma plane has full frame dimensions; the U and
V chroma planes each have half width and half height. The command-line encoder requires
positive width and height that are multiples of 16, a whole number of complete frames, and a
positive optional worker count; four workers are the default. It writes a proprietary sequence
of `FRM1` frame records. A matching decoder reconstructs raw YUV420 from that stream
[2], [3].
The evaluation question is not whether this system matches H.264 or JPEG quality. It is
whether the implemented codec is internally consistent, whether legal dependencies are
preserved by pthread scheduling, and what the checked-in measurements show for a defined
short workload. In this framing, compression ratio and parallel speedup are workload-specific
measurements, not evidence of general-purpose codec superiority.
2. Problem, objectives, and requirements
2.1 Problem statement
Implement an end-to-end lossy transform codec whose encoder and decoder derive identical
predictors from reconstructed samples, while allowing independent row jobs and frames to
execute concurrently. The core correctness hazard is causal: a block may not be predicted
until all boundary pixels it uses have been reconstructed. A second hazard is output ordering:
worker completion order is not necessarily frame order.

3. Background and related work
3.1 Transform coding and quantization
The DCT maps spatial samples into frequency coefficients. Ahmed, Natarajan, and Rao
established the DCT as a useful orthogonal transform for digital signal processing and
showed rate-distortion behaviour close to the Karhunen–Loève transform for relevant signal
models [10]. This repository applies an orthonormal 8×8 DCT-II to prediction residuals. Its

two-pass implementation transforms rows then columns, reducing the arithmetic order from
O(N⁴) for a direct two-dimensional sum to O(N³) for a separable transform.
Quantization is lossy: each coefficient is divided by a fixed frequency-dependent integer table
and rounded. The table in `src/codec.c` has the familiar JPEG luminance-table values, but
using those numbers does not make the implementation JPEG-compliant. The code applies
the table to its own residual coefficients and then uses its own RLE symbols and frame record
format [3]. There is no quality-factor control or target-rate controller in the current interface.
3.2 Run-length and Huffman coding
Zig-zag scanning tends to place higher spatial frequencies later in a block, where quantization
often creates a run of zeros. The encoder records each nonzero quantized coefficient as a pair
containing its preceding zero count and value, plus a terminating pair for a zero tail. Huffman
coding then assigns prefix codes using the observed frequency of each distinct pair.
Huffman’s original minimum-redundancy construction provides the theoretical basis for this
entropy stage [11].
The repository favours transparent deterministic implementation over optimal data structures:
symbol discovery and lookup use linear searches, while tree construction repeatedly scans
active nodes. Consequently, coding overhead can become material as the frame-level
alphabet grows. The report treats this as a scalability limitation, not as a defect in the basic
prefix-code idea.
3.3 Parallel video coding and causal wavefronts
Research on H.264 decoding and HEVC wavefront parallel processing shows that coding
dependencies constrain scaling and that scheduling overhead can limit otherwise abundant
block-level work [12], [13]. This project borrows the general scheduling idea, not a standard-
specific codec design: a row proceeds left-to-right, and a block waits until the block above
has published the required reconstructed boundary. Its dependency graph is acyclic because
edges point only to top and left neighbours. Amdahl’s analysis supplies a complementary
warning: serial work and coordination place limits on achievable speedup as worker count
grows [14].
The distinction matters. H.264 specifies prediction modes and syntax; JPEG specifies
marker-based image-coding syntax and related coding processes [15], [16]. Here a simplified
DC-like neighbour average, a floating-point DCT, a fixed quantizer, RLE-pair Huffman

4. Architecture and data flow
Figure 1. Architecture reconstructed from src/main.c, src/threadpool.c, src/wavefront.c, src/reorder.c, src/codec.c, and
src/decode.c.
`src/main.c` owns the encoder orchestration. For every frame, `FrameWork` stores the
original and reconstructed YUV420 buffers, row-output slots, per-plane `WavefrontSync`
objects, completion state, and pipeline error state. A producer submits one job per block row,
plane, and frame. Jobs hold direct frame pointers, so workers do not need a global frame
lookup. The queue in `src/threadpool.c` is a circular array with capacity four times the
configured worker count and has `not_empty`/`not_full` condition variables for backpressure
[2], [4].
Each row worker processes its row from left to right. It writes RLE results to a deterministic
block index, reconstructs the same block into its plane-specific reconstruction view, and
publishes progress at the configured synchronization granularity. The last completed row
finalizes a frame by concatenating block RLE records in plane/raster order and Huffman-
coding that combined sequence. `src/reorder.c` owns a slot per frame and a writer thread that
emits only the next expected frame number [2], [5], [6].
The decoder (`src/decode.c` and `src/decode_main.c`) parses a `FRM1` record, reconstructs
the deterministic Huffman tree from the transmitted symbol table/frequencies, decodes RLE
pairs, restores quantized coefficient blocks, dequantizes and inverse-transforms them, and

5. Codec implementation and pseudocode audit
5.1 Encoder block path
The production path in `encode_plane_row()` is the implementation reference for the report
pseudocode [2]. It obtains the current plane’s source and reconstruction pointers, creates a
`Frame` view whose dimensions match that plane, waits on the wavefront dependency,
predicts a scalar boundary average, subtracts it from each source pixel, applies
`dct_transform()`, quantizes, RLE-encodes, saves the pairs, and calls `reconstruct_block()`
before publishing progress. The reconstruction function dequantizes the quantized
coefficients, calls the inverse DCT, adds the predictor, rounds, clips to [0, 255], and writes
the plane reconstruction buffer [3].
for each plane (Y, U, V):
for each block row r and each frame f:
submit row-job(f, plane, r)
worker(row-job):
for column c from left to right:
wait until r == 0 or progress[r - 1] > c
p = mean(available reconstructed top and left boundaries)
residual = source_block - p
q = quantize(DCT(residual))
store zigzag-RLE(q) in its frame/block slot
recon_block = clip(p + IDCT(dequantize(q)), 0, 255)
write recon_block before publishing row progress
decrement this frame's outstanding-row count
if final row: concatenate all block pairs, Huffman-code, submit frame
writer: emit only the next expected frame-number slot
The pseudocode matches the main control flow, with two clarifications that prevent common
overstatements. First, entropy coding is frame-wide and happens only after all plane rows for
that frame finish; it is not a separate Huffman stream per block. Second, the code schedules
rows as jobs, while the row job performs a sequential column loop gated by a top-row
progress condition. This is row-job wavefront scheduling, not a global queue of independent
block jobs.
5.2 Predictor, boundaries, and reconstruction consistency
For the top-left block, the predictor is 128. For blocks with one available neighbour, it
averages the eight reconstructed samples along that boundary. For interior blocks, it averages
the eight top-boundary samples and eight left-boundary samples together using integer

The block is reconstructed immediately after quantization and before a progress update. In

5.3 Frame syntax and standards claim audit
The writer serializes the four-byte `FRM1` marker, frame number, block count, Huffman
symbol count, coded bit count, each symbol/frequency entry, and the packed payload in big-
endian integer order [3], [6]. This is sufficient for the paired decoder’s project-specific
contract, but it is not JPEG marker syntax, an H.264 NAL-unit bitstream, or an MP4
container. No standard decoder compatibility is established.
The `demo.sh` script invokes FFmpeg around the custom encoder: it extracts YUV420 input,
runs the custom binary, decodes the custom file, and may wrap the decoded result as an
H.264 MP4 preview for ordinary playback [9]. An H.264 preview container is not evidence
that the custom encoder implements H.264. Likewise, use of DCT, zig-zag, Huffman coding,
and a JPEG-like quantization table is not sufficient evidence of JPEG conformance [15], [16].
6. Parallel scheduling and pthread synchronization
6.1 Queue and worker lifecycle
The queue’s head, tail, and count are guarded by a mutex. A consumer checks emptiness in a
`while` loop and sleeps on `not_empty`; after removing a job, it signals `not_full`. Producers
wait while the queue is full, then enqueue and signal a consumer [4]. On normal shutdown,
`threadpool_destroy()` queues one sentinel per worker, joins the workers, destroys the
condition variables and mutex, and frees the queue. This separates work submission from the
worker lifecycle and bounds the number of queued jobs.

6.2 Wavefront correctness
Figure 2. Illustrative block grid. A block can run after its top dependency is published; left dependency is satisfied by the
row worker’s left-to-right traversal.
For block (r,c), `wavefront_wait_for_dependency()` waits while `row_progress[r-1] <= c`,
under the same mutex used by `wavefront_mark_done()` to update progress. The `while`
predicate is necessary because a condition-variable wakeup does not prove that the specific
row/column dependency is now satisfied. The first row bypasses the wait. Once
reconstruction is complete, `wavefront_mark_done()` stores at least c+1 and broadcasts on
the shared condition variable [5].
A broadcast is deliberate because many rows share one condition variable but have different
eligibility predicates. A signal could wake a row that is still ineligible while another eligible
row remains asleep. Broadcast makes all waiters reevaluate their own predicates, at the cost
of unnecessary wakeups and possible thundering-herd behaviour. The mutex protects the
progress value and makes the predicate check/update atomic relative to waiters; the condition
wait releases and reacquires the mutex as specified by POSIX [17].

6.3 Ordered frames and lifetime
Frames can finish out of order. Each completed frame transfers ownership of its encoded
bitstream to a numbered reorder slot. The writer waits until
`slots[next_expected_frame].ready`, removes that bitstream under the reorder mutex,
advances the expected index, and writes it outside the critical section. The design decouples
processing completion from output order [6]. The encoder currently reads all input frames
into memory before creating the pool, so whole-file memory use scales with input duration;
the reorder slots also scale with frame count. This is correctness-friendly for the short
benchmark but limits streaming scalability.

9. Theoretical performance analysis
9.1 Transform work and block counts
For an N×N DCT, direct evaluation computes N² outputs, each summing N² input
contributions, which is O(N⁴). The separable row/column implementation performs 2N one-
dimensional transforms, each with N² terms, or O(N³). At N = 8 this is 4,096 versus 1,024
multiply-accumulate terms in the core transform arithmetic, a nominal fourfold reduction.
This count excludes basis construction, memory movement and function overhead.
`build_dct_basis()` is called by both the forward and inverse transform, so recomputing the
cosine basis for each block adds avoidable work; precomputing a shared immutable basis is a
credible optimization [3].
For an image of W×H samples in YUV420, the number of 8×8 blocks is WH/64 for Y plus
two planes of (WH/4)/64, totalling 3WH/128. At 1280×720 this equals 21,600 blocks per
frame: 14,400 luma blocks and 3,600 each for U and V. Three frames therefore process
64,800 blocks. Per-block transform, quantization, RLE and reconstruction are O(8²), while
the current frame Huffman preparation uses linear scans; if M is the number of RLE pairs and
S the number of distinct symbols, symbol counting can approach O(MS) and active-node
selection O(S²) [3].
9.2 Wavefront critical path and average parallelism
For one plane with R block rows and C columns, there are RC block operations. Under a
simple unit-cost DAG model with only top and left dependencies, the critical path comprises
R + C − 1 diagonal steps. The average-parallelism ceiling RC/(R + C − 1) is therefore about
57.8 for luma (R = 90, C = 160) and about 29.0 for each chroma plane (R = 45, C = 80).
These are theoretical task-graph averages assuming unlimited processors and zero
scheduling/synchronization cost, not attainable speedup claims. The implementation
schedules whole rows and uses finite workers, and also pays for setup, frame-wide Huffman
coding, queue operations, output ordering and file I/O.
The diagonal wavefront begins narrow, widens as upper rows make progress, and narrows
again at the far edge. This ramp-up/ramp-down profile plus synchronization and serial work
explains why the measured eight-worker speedup (3.60×) falls well below ideal 8×.
Amdahl’s law captures the general ceiling from serial portions [14], but fitting a single serial

10. Limitations and future work
10.1 Verified and evidence-related limitations
 The encoder requires raw YUV420 and dimensions divisible by 16; normal compressed
video requires an external conversion/preview path.
 All frames are loaded before jobs are submitted, and reorder slots are allocated per input
frame. Memory therefore grows with clip duration rather than a bounded streaming
window.
 Frames are independently coded; there is no motion estimation, inter-frame prediction,
rate control, target bit rate or standard container support.
 The fixed quantizer and the use of one table for Y/U/V constrain quality control; PSNR
alone cannot establish subjective visual quality.
 Linear Huffman-symbol searches and repeated tree-node scans may become expensive on
larger or more varied inputs; transform bases are also recomputed frequently.
 The original timings use a very short workload and coarse time resolution. Granularity
results are means-only in the retained CSV, and performance claims are from one
platform/corpus.
 The accessible retained data did not allow independent recomputation of the production
PSNR or re-execution of tests/Helgrind in this audit.
10.2 Recommended improvements
First, retain a reproducible experiment bundle: raw input clip, decoded output, commands,
compiler version/flags, macro settings, executable hash, and per-run timing samples for every
campaign. Include the exact number of runs and report mean, median, standard deviation and
preferably confidence intervals for short timings. Use a monotonic high-resolution timer and
repeat longer clips or multiple content classes to reduce timing quantization.
Second, reduce redundant work by precomputing the DCT basis and replacing linear
Huffman symbol lookup with a hash table and the minimum-node scan with a priority queue.
Profile before implementing, because the small current workload may be dominated by setup
or I/O. Third, introduce a bounded streaming frame window with explicit lifetime/accounting
around row jobs and reorder slots; retain strict output order and the serial output baseline as
regression criteria.
Fourth, broaden validation: malformed/truncated `FRM1` inputs, extreme dimensions and

11. Conclusion
The inspected source implements a self-contained educational lossy YUV420 codec with an
8×8 separable DCT, fixed quantization, zig-zag RLE, per-frame Huffman coding and a
custom `FRM1` record format. Its key parallel design is internally coherent at source level:
row workers process columns in causal order, use reconstructed top/left boundaries, guard
wavefront progress with a mutex, wait in predicate loops, and publish after reconstruction;
the reorder writer preserves frame-number order even when workers finish out of order.
These are project-specific mechanisms, not JPEG or H.264 conformance.
The benchmark CSVs substantiate the stated means and the compression arithmetic. On the
documented short input, 8 workers reached 3.60× speedup with 45.0% efficiency, while
causal prediction reduced compressed size by 29.74% relative to the constant-128 version.
The separate granularity averages favour per-block publication at 4 and 8 workers, but they
lack per-run samples. The claimed PSNR, compiler, test and Helgrind observations remain
repository-reported rather than independently reproduced here. The strongest next step is not
a broader performance claim but a reproducible evidence bundle, followed by longer multi-
content benchmarks and memory/performance improvements.
